# tosir — комплект навыков для агентской разработки

tosir организует выполнение задачи через общий план, проверяемые этапы реализации и независимое ревью.

Состояние сохраняется в файлах задачи, а не только в истории чата.
Это позволяет выполнять операции в отдельных сессиях, использовать разных агентов и моделей и продолжать работу после остановки.

Комплект включает основной цикл разработки и два необязательных
навыка вне цикла: уточнение задачи и рефлексию.

## Состав

| Навык | Назначение |
|---|---|
| [tosir](tosir/SKILL.md) | Общий регламент, форматы файлов, состояния и переходы |
| [tosir-overview](tosir-overview/SKILL.md) | Исследование проекта и создание общего плана |
| [tosir-plannextstage](tosir-plannextstage/SKILL.md) | Подробное задание для очередного этапа |
| [tosir-implementstage](tosir-implementstage/SKILL.md) | Реализация этапа или доработки с проверками |
| [tosir-reviewstage](tosir-reviewstage/SKILL.md) | Приёмка этапа или подготовка задания на исправления |
| [tosir-review](tosir-review/SKILL.md) | Итоговая приёмка всей задачи |
| [tosir-workflow](tosir-workflow/SKILL.md) | Управление полным циклом через специализированных субагентов |
| [tosir-grill](tosir-grill/SKILL.md) | Уточнение задачи в диалоге до начала цикла |
| [tosir-reflection](tosir-reflection/SKILL.md) | Разбор процесса после выполнения задачи |

README описывает использование комплекта. Точные правила операций находятся в соответствующих SKILL.md; таблица переходов и форматы журнала — в tosir.

## Общая схема

```text
До цикла, необязательно:
  tosir-grill → уточнённый task.md

Основной цикл:
  tosir-overview
    ↓
  tosir-plannextstage
    ↓
  tosir-implementstage ←─────────────┐
    ↓                                │
  tosir-reviewstage                  │
    ├─ нужны исправления ────────────┘
    ├─ блокировка → решение пользователя
    └─ принято → коммит → планирование следующего этапа

  Все этапы приняты:
    tosir-review
      ├─ пробелы → планирование дополнительного этапа
      ├─ блокировка → решение пользователя
      └─ TASK_DONE

После цикла, необязательно:
  tosir-reflection → reflection.md
```

Планирование, реализация и ревью — операции цикла.
Этап — проверяемый результат реализации. Простая задача может состоять из одного этапа.

## Подготовка

Сделайте навыки доступными в используемом агентском инструменте.

Для выполнения задач агентам нужны доступ к рабочим репозиториям, возможность читать и записывать файлы задачи и запускать предусмотренные проверки.

Для автоматического цикла дополнительно нужны:
- основной агент-оркестратор с возможностью вызывать субагентов;
- специализированные агенты для планирования, реализации и ревью;
- соответствие имён агентов таблице в tosir-workflow.

Комплект не назначает модели. Модели, инструменты и задаются в конфигурации используемых агентов.

## Быстрый старт

### 1. Опишите задачу

Создайте папку задачи и task.md, например:

```text
.agents/tasks/my-task/task.md
```

Запишите желаемый результат, требования, ограничения и критерии завершения. При необходимости укажите этапы и их количество: обязательное это ограничение или предпочтительный вариант.

### 2. При необходимости уточните задачу

До начала цикла запустите в основной диалоговой сессии:

```text
Загрузи tosir-grill и уточни задачу.

Папка задачи: .agents/tasks/my-task
Рабочий репозиторий: /полный/путь/к/проекту
```

Навык задаёт вопросы по одному, предлагает рекомендуемые ответы и проверяет факты по проекту.

После подтверждения итоговой сводки он переписывает task.md.
Исходный текст сохраняется в task-source.md, если такого файла ещё нет.

Если overview.md или log.md уже существует, grill не изменяет задачу: цикл считается начатым.

### 3. Запустите полный цикл

Выберите оркестратор основным агентом и отправьте:

```text
Загрузи tosir-workflow и выполни полный цикл.

Папка задачи: .agents/tasks/my-task
Рабочий репозиторий: /полный/путь/к/проекту

Начни с определения текущего состояния.
Разрешаю автоматические переходы по регламенту и коммиты принятых этапов агентом ревью.

Push и deploy не разрешаю.
```

Оркестратор определяет следующую операцию по журналу и запускает каждую операцию в новой дочерней сессии. Операции выполняются последовательно.

Запуск полного цикла по tosir-workflow уже предусматривает автоматические переходы и коммиты принятых этапов.
В примере эти разрешения повторены явно.

### 4. При необходимости выполните рефлексию

После завершения задачи запустите отдельно:

```text
Загрузи tosir-reflection и разбери выполненную задачу.

Папка задачи: .agents/tasks/my-task
```

Навык анализирует доработки, остановки и пробелы итоговой приёмки:
почему они возникли, можно ли было их избежать и что изменить
в процессе.

Результат сохраняется в reflection.md. Код, планы и журнал не изменяются; рекомендации автоматически не применяются.

## Ручное выполнение операций

Оркестратор необязателен. Операции можно запускать вручную, каждую — отдельным запросом подходящему агенту.

Общий формат:

```text
Загрузи навык <имя навыка> и выполни только эту операцию.

Папка задачи: .agents/tasks/my-task
Рабочий репозиторий: /полный/путь/к/проекту
```

Начните с tosir-overview. Дальнейшую операцию определяйте по состоянию log.md и таблице переходов tosir.

Операционный навык сам по себе не означает разрешение выполнить весь цикл.

## Агенты автоматического цикла

tosir-workflow выбирает первого доступного агента в строке, слева направо:

| Операция | Приоритет агентов |
|---|---|
| overview, plannextstage | planner → architect |
| implementstage | builder → maker → implementer → developer |
| reviewstage, review | reviewer → checker → tester |

Если у вас другие имена агентов, измените таблицу в tosir-workflow.

Навыки операций описывают процесс, а не настройки конкретных моделей. Связь операций с агентами находится в workflow.

tosir-grill и tosir-reflection запускаются вручную и не включены в автоматический цикл.

## Файлы задачи

```text
my-task/
├── task.md          # требования; после создания overview неизменяемы
├── task-source.md   # исходный текст перед уточнением через grill
├── overview.md      # общий план, перечень и количество этапов
├── stage-01.md      # контракт и подробный план первого этапа
├── stage-01-1.md    # самодостаточное задание на доработку
├── stage-02.md      # следующий основной этап, если нужен
├── log.md           # состояние и история операций
├── memory.md        # короткие находки и заметки агентов
└── reflection.md    # необязательный разбор процесса
```

Это пример: файлы создаются по мере необходимости.
Вторая стадия, доработки, исходная копия и рефлексия нужны не каждой задаче.

### План и состояние — разные вещи

- task.md задаёт требования пользователя.
- overview.md фиксирует общую декомпозицию.
- stage-NN.md задаёт контракт приёмки этапа.
- stage-NN-M.md содержит все оставшиеся исправления.
- log.md определяет состояние задачи и следующую операцию.

Наличие плана, отчёта или коммита само по себе не означает,
что этап принят.

## Как ограничивается контекст

- Оркестратор управляет состоянием и делегированием, а не выполняет работу субагентов.
- Каждая операция автоматического цикла получает новую сессию.
- При полном пакете запуска от оркестратора исполнитель не читает журнал: необходимые параметры передаются в задании.
- Для доработки исполнитель читает текущий самодостаточный план, а не всю историю этапа.
- Ревьюер сохраняет исходный контракт этапа и текущую доработку как основу проверки всего результата.
- Код и дополнительные документы читаются по необходимости.

При ручном запуске исполнитель получает недостающие параметры из журнала. Проверка фактического состояния Git выполняется независимо от способа запуска.

## Остановки и продолжение

Цикл не обходит блокировки. При неоднозначных требованиях, противоречиях, остановке реализации или заблокированном ревью требуется решение пользователя.

Решение фиксируется в log.md записью USER_DECISION с разрешённым следующим шагом и необходимыми параметрами.
После этого цикл можно запустить повторно с указанием той же папки задачи.

Не удаляйте журнал и существующие планы ради перезапуска: они нужны для корректного продолжения.

## Коммиты и границы действий

- Принятый этап должен быть закоммичен до начала следующего.
- При полном цикле коммит выполняет агент ревью после приёмки.
- REVIEW_ACCEPTED подтверждает приёмку реализации, но не успешное создание коммита.
- Если коммит не выполнен, автоматический цикл останавливается.
- Разрешение коммитить не означает разрешения на push и deploy.
- Пользовательские изменения нельзя перезаписывать.
- Требования проекта и ограничения окружения сохраняют силу при выполнении проверок.

## Принципы

- Минимальное достаточное число этапов, без искусственного дробления.
- Проверяемые требования вместо неявных предположений.
- Планирование по фактическому коду и доступным средствам проверки.
- Самодостаточные задания для исполнителей.
- Приёмка всего этапа, а не только последнего исправления.
- Состояние в артефактах, а не только в памяти модели.
- Уточнение задачи и рефлексия — по необходимости, вне цикла.
